================================================================
1. 書き方のルール
================================================================

  Claudeへの指示は具体的であるほど品質が上がる。

  良い書き方：
    具体的・箇条書き・コード例あり

  悪い書き方：
    「改善できます」など曖昧な表現
    根拠のない指摘

  例：

    NG：
      このメソッドは改善できます

    OK：
      N+1が発生しています。
      高負荷時にDB接続枯渇のリスクあり（P1）
      → findAllById() を使ってバッチ取得に変更すること


================================================================
2. Forbidden セクションの重要性
================================================================

  Forbidden セクションには
  やってはいけないことを具体的に書く。

  NG例を具体的に書くほど出力品質が安定する。

  書き方例：

    # Forbidden
    - 「改善できます」だけの曖昧表現
      NG: "このメソッドは改善できます"
      OK: "N+1が発生しています。高負荷時にDB接続枯渇のリスクあり(P1)"

    - 根拠なし指摘
      NG: "このコードは危険です"
      OK: "@Transactional内で外部APIを呼び出しています。
           外部障害時にロックが保持され続けるリスクあり(P1)"

    - 影響範囲の未記載
      必ず「どのテーブル・API・サービスに影響するか」を記載すること

    - リスク分析なし
      P0〜P3のレベル分類なしの指摘は禁止


================================================================
3. セクションの順番
================================================================

  Claudeは上から順に読む。
  Purposeが最初にないと役割を誤解する場合がある。

  推奨する順番：

    @skill: xxx           ← 識別タグ（最初に宣言）
    @tier: 1

    # Purpose             ← 1番最初に書く（最重要）
    # Auto Load Condition ← いつロードされるか
    # Risk Pattern        ← 何を検出するか
    # Severity Rule       ← 重要度の判定基準
    # High Risk Combination ← 複合リスクの定義
    # Forbidden           ← やってはいけないこと
    # Detection Note      ← 補足・注意事項

  Purpose を最初に書く理由：
    Claudeはファイルの冒頭で
    「自分が何をするSkillか」を把握する。
    冒頭が曖昧だと後半の指示の解釈がブレる。


================================================================
4. コード例の効果
================================================================

  危険パターンと安全パターンを
  両方書くと検出精度が上がる。

  悪い書き方：
    @Transactional の伝播設定に注意する

  良い書き方：

    危険パターン：
      @Transactional(propagation = Propagation.REQUIRES_NEW)
      // JobRepositoryのトランザクションと競合する

    安全なパターン：
      @Transactional
      // 伝播設定なし・デフォルト（REQUIRED）のまま使う

  コード例を書くメリット：
    ・Claudeが具体的なコードパターンを認識できる
    ・誤検出が減る
    ・修正推奨の精度が上がる


================================================================
5. Skill 間の依存関係
================================================================

  関連するSkillを明示することで分析漏れを防げる。

  書き方例：

    # Detection Note
    このSkillは transaction_skill と併用すること。
    デッドロックはトランザクション設計と切り離せないため
    transaction_skill の分析結果を前提として判断する。

  依存関係を書くべきケース：
    ・2つのSkillが組み合わさって初めて判断できる場合
    ・片方だけでは誤検出が起きやすい場合
    ・前提となる知識が別Skillにある場合


================================================================
6. Platform Skill との役割分担
================================================================

  platform_skill.md   → 全体の判断基準・禁止事項・出力形式
  各 skill.md         → 個別の専門知識・リスクパターン

  重要なルール：

    platform_skill に書いたことを
    各 skill で上書きしてはいけない。

  例：

    platform_skill.md：
      「影響範囲を必ず記載すること」

    各 skill.md：
      「影響範囲は不要」← これは矛盾・禁止

  役割の分担：

    platform_skill.md が担うもの：
      ・P0〜P3の定義
      ・出力フォーマット
      ・禁止事項（全Skillに共通）
      ・レビューの優先順位

    各 skill.md が担うもの：
      ・個別のリスクパターン
      ・Auto Load Condition
      ・そのSkill固有のForbidden


================================================================
7. md ファイルのサイズ
================================================================

  1ファイルの推奨サイズ：

    Skill  → 100〜300行
    Agent  → 50〜150行
    Prompt → 30〜80行

  大きすぎた場合の問題：

    ・Promptの上限（token数）を圧迫する
    ・Claudeが後半を読み飛ばす可能性がある
    ・レビュー品質が不安定になる

  小さすぎた場合の問題：

    ・指示が曖昧になる
    ・Claudeが正しく役割を理解できない
    ・誤検出・検出漏れが増える

  サイズが大きくなりすぎた場合の対処：

    ・Risk Pattern を tier ごとに別ファイルに分割する
    ・使用頻度の低いパターンは Tier 3 に移動する
    ・コード例は最小限に絞る
